# RFC: oh-my-gamepad

Статус: черновик для обсуждения.

## Идея

oh-my-gamepad — программа на Rust для управления компьютером с контроллера Xbox Series. Первая версия рассчитана на macOS. Как и в Vim, назначение кнопок зависит от режима. Имена режимов, переходы и поведение стиков задаются в YAML. В `example/config.yaml` есть готовая раскладка для первого запуска.

Одновременно активен один режим. Программа начинает с `initial_mode`. Действие смены режима срабатывает при нажатии, а новый режим остаётся активным после отпускания. В примерной раскладке одна и та же кнопка возвращает в `normal` из любого другого режима.

## Среда выполнения и сервис ввода

Основная программа на Rust читает YAML, загружает плагины и создаёт один сервис ввода. Он хранит текущий режим, состояние контроллера и активные поведения. Сервис создаёт события ввода и смены режимов, а среда добавляет события по таймеру и события запуска и завершения. Event Dispatcher доставляет их обработчикам, а Action Performer выполняет возвращённые действия.

Для первой версии предлагается такой состав:

| Компонент | Зона ответственности |
| --- | --- |
| Адаптер ввода `gamepad` | Читает данные контроллера из macOS и передаёт сервису измерения и состояние подключения. |
| Сервис ввода | Сравнивает новые измерения с текущим состоянием, применяет назначения, меняет режимы и готовит события для диспетчера. |
| `builtin_primitives` на Rust | Особый встроенный плагин с доступом к системным операциям. Отправляет ввод в macOS и вызывает смену режима через сервис ввода. |
| `mouse` и `chord_text` на Lua | Реализуют конкретные поведения указателя, прокрутки и ввода текста. |
| `logger` на Rust | Принимает сообщения и пишет их в журнал. |

### Что хранит и делает сервис ввода

1. **Хранит подготовленные режимы.** При запуске программа проверяет `initial_mode`, входы в `mappings` и ссылки на режимы и плагины. Она передаёт сервису готовую таблицу назначений и поведений. Каждый плагин может проверить собственные параметры в `load`.
2. **Обрабатывает ввод.** Сервис обновляет состояние контроллера и определяет, что изменилось. Он передаёт Action Performer назначение из режима, активного на момент ввода. События ввода затем направляются по поведению, активному после выполнения назначения.
3. **Меняет режимы.** Сервис проверяет целевой режим, обновляет активные поведения и создаёт события перехода. При выходе из поведения запрашивает снятие его удержаний. При отключении контроллера сбрасывает состояние ввода.

### Как действие приводит к событию

`builtin_primitives` при запуске получает доступ к тому же экземпляру сервиса, который обрабатывает ввод. Действие `builtin_primitives.change_mode` вызывает метод смены режима с именем цели. Сервис проверяет цель по таблице и обновляет состояние. Если режим действительно сменился, сервис ставит в очередь `mode_changed` и события выхода и входа для поведений. Повторный запрос текущего режима оставляет его активным. Вызывать `change_mode` можно после начальной активации, в том числе из обработчика `ready`.

Например, при отклонении стика в `normal` сервис находит действие `builtin_primitives.change_mode` с аргументом `text`. Action Performer выполняет его, сервис переключает режим, а диспетчер доставляет события перехода. Затем `stick_moved` получает плагин поведения этого стика в `text`.

## Конфиг

Программа ищет пользовательский конфиг в `~/.config/oh-my-gamepad/config.yaml`, а Lua-плагины — в `~/.config/oh-my-gamepad/plugins/`. В MVP файл `config.yaml` обязателен. Если его нельзя прочитать или разобрать, программа сообщает об ошибке и завершает работу с кодом 1. Для первого запуска можно скопировать пример на этот путь. Запуск из проекта — `cargo run --locked`. Для отправки клавиатурного и мышиного ввода macOS должен разрешить универсальный доступ.

Среда загружает все файлы `*.lua`, которые лежат непосредственно в `plugins/`. Один файл — один плагин со своим экземпляром Lua. Имя берётся из имени файла без `.lua`. Например, `chord_text.lua` загружается как `chord_text`. В YAML имя используется в назначениях, поведениях и настройках уже обнаруженного плагина. Вспомогательные функции на этом этапе хранятся внутри файла каждого плагина.

Каталог [example/](example/) предназначен для личной раскладки автора и её плагинов. В [example/config.yaml](example/config.yaml) `normal` переключается на `mouse` по `LB` и на `text` при отклонении любого стика. Из `mouse` и `text` кнопка возврата — правый курок `RT`. Исходники `mouse.lua` и `chord_text.lua` лежат в `example/plugins/` и встраиваются в программу при сборке. Пользовательский файл с таким же именем заменяет встроенный плагин. На машине автора `~/.config/oh-my-gamepad` указывает на `example/` через символическую ссылку. Правки в репозитории видны программе по этому пути при следующем запуске.

- `mappings` связывает ввод с разовым действием. В примере `ls` и `rs` обозначают отклонение стика за порог. Физические кнопки под стиками — LSB (Left Stick Button) и RSB (Right Stick Button). В конфиге и событиях используются имена `lsb` и `rsb`, как и `lb` и `rb`. Курки `lt` и `rt` используются в назначениях как кнопки с порогом 30%.
- `buttons.<имя>.behavior` задаёт поведение кнопки в режиме. Можно задать действие через `mappings`, поведение через `buttons` или оба сразу. Поведение получает события нажатия и отпускания.
- `sticks.left.behavior` и `sticks.right.behavior` выбирают обработчик для каждого стика по паре `plugin` и `type`. Это настройка того, как плагин читает стик в данном режиме.
- Для курков используются такие же настройки `triggers.left.behavior` и `triggers.right.behavior`. Их можно задавать отдельно для каждого курка и режима.
- Секция `chord_text` принадлежит плагину. Он может читать весь разобранный конфиг и проверяет свои настройки. Общие правила для режимов и назначений проверяются при запуске программы.

В MVP каждое назначение содержит `input` и `action`. В `action` явно задаются `plugin`, `type` и список `arguments`. Для действия без аргументов используется `arguments: []`.

```yaml
- input: lb
  action:
    plugin: builtin_primitives
    type: change_mode
    arguments:
      - mouse
```

Эта же структура действия используется в списках, которые возвращают плагины.

## Действия и Action Performer

Действие — разовая операция, например клик мыши, ввод символа или смена режима. Его можно взять из `mappings`, получить от плагина в ответ на событие или получить как результат другого действия. Везде используются три поля: `plugin`, `type` и `arguments`. Аргументы — список обычных значений YAML, включая строки, числа, списки, словари и `null`. Общая схема принимает произвольные аргументы. Их смысл и допустимые значения проверяет обработчик действия. В Lua значение `null` доступно как `yaml_null`. Функция `pairs` обходит словари конфига в порядке YAML.

Action Performer находит обработчик по имени из поля `plugin`. Плагин сам разбирает `type` и `arguments`. При неизвестном типе действия обработчик возвращает ошибку. Например, `chord_text` обрабатывает `uppercase` как изменение настройки регистра, а для вывода подтверждённого символа возвращает действие `builtin_primitives.type_text`.

`builtin_primitives` выполняет `change_mode` и системные действия `key`, `key_down`, `key_up`, `mouse_key`, `move_pointer`, `scroll` и `type_text`. Действие `key` делает короткое нажатие клавиши. `key_down` нажимает клавишу, а `key_up` отпускает её. Каждое действие выполняется сразу. Состояние нажатой клавиши сохраняется между `key_down` и `key_up`. Эти три действия принимают имя клавиши или её код macOS. `mouse_key` принимает `left`, `right` или `middle` и необязательную операцию `click`, `down` или `up`. По умолчанию это `click`. `move_pointer` принимает смещения `dx` и `dy` в точках. Положительные значения двигают указатель вправо и вниз. `scroll` принимает два целых смещения в пикселях. `type_text` принимает строку.

Действия одного списка выполняются по порядку. Если обработчик вернул вложенные действия, они выполняются перед следующим пунктом исходного списка. Например, если `A` возвращает `A1` и `A2`, то список `[A, B]` даёт порядок `A → A1 → A2 → B`. Предлагается ограничить глубину и общее число действий за одну цепочку. Ошибка останавливает остаток цепочки и попадает в журнал. Уже выполненные действия сохраняют свой эффект.

### Мышь

В режиме `mouse` кнопки `LB` и `RB` удерживают левую и правую кнопки мыши. Нажатие `LB`, которым открыли этот режим, только переключает режим. Отдельное действие `builtin_primitives.mouse_key` с аргументом `left` или `right` по-прежнему делает обычный клик.

Для удержания у кнопки геймпада задаётся поведение плагина `mouse`. Тип `left_hold` удерживает левую кнопку мыши, `right_hold` — правую. При выходе из режима или отключении контроллера программа отпускает удерживаемые кнопки.

Движение и прокрутка настраиваются отдельно в `mouse.pointer` и `mouse.scroll`. `sensitivity` задаёт скорость в пикселях в секунду при полном отклонении. `acceleration: 1` даёт линейную реакцию, а значение больше 1 замедляет небольшие движения и сохраняет полную скорость при отклонении до края. `dead_zone` задаёт радиус неподвижной зоны от 0 до 1. `invert_x` и `invert_y` меняют направление соответствующих осей. Любую из этих настроек можно переопределить в `behavior.settings` конкретного стика. Пример значений есть в [раскладке](example/config.yaml).

### Пример поведения кнопки

В режиме `mouse` кнопка X может удерживать Shift. В этом примере плагин `keyboard` сам определяет смысл типа `hold` и настройки `key`.

```yaml
modes:
  mouse:
    buttons:
      x:
        behavior:
          plugin: keyboard
          type: hold
          settings:
            key: shift
```

На `button_pressed` плагин возвращает `builtin_primitives.key_down` с аргументом `shift`, а на `button_unpressed` — `builtin_primitives.key_up` с тем же аргументом. Так можно зажать X и пользоваться стиком или нажимать другие кнопки, пока Shift удерживается.

Среда присваивает каждой активации поведения идентификатор и передаёт его действиям из обработчиков этого поведения. `builtin_primitives` хранит удержания по этому идентификатору. `key_up` снимает удержание того же поведения. При выходе среда запрашивает снятие всех удержаний этой активации, даже если кнопку геймпада ещё держат. Если одну клавишу удерживают несколько поведений, `builtin_primitives` отпускает её в системе после окончания последнего удержания.

## Общий интерфейс плагинов

При загрузке ядро регистрирует плагин по уникальному имени. Поле `type` в действии или поведении — строка, смысл которой определяет сам плагин. Например, плагин `mouse` получает `behavior.type = "scroll"` и сам решает, как обработать ввод для такого поведения.

Поле `behavior.arguments` принимает позиционные значения YAML в том же формате, что `action.arguments`. Плагин определяет их смысл. Если поле пропущено, обработчик получает пустой список.

Rust и Lua используют один контракт:

- Обработчик события получает событие и контекст. Он может вернуть упорядоченный список действий, в том числе пустой.
- Плагин может предоставить один обработчик `on_action(action, context)` для всех своих действий. Обработчик на Rust может выполнить операцию напрямую, как это делает `builtin_primitives`, или вернуть другие действия. Обработчик на Lua запрашивает системные операции через действия, которые предоставляет программа.

Первая версия `mouse` и `chord_text` пишется на Lua. `mouse` читает отклонения стиков и возвращает действия движения и прокрутки. `chord_text` выбирает символ и возвращает действие ввода текста. Позже любой из них можно перенести на Rust, сохранив имя плагина, типы действий и поведений, аргументы и формат его секции YAML.

### Загрузка и выгрузка

У Rust-плагина есть методы `load(context)` и `unload(context)`. У Lua-плагина это функции `event_handlers.load` и `event_handlers.unload`. Они необязательны и могут вернуть действия, как обычный обработчик.

1. Среда читает YAML и узнаёт имена Lua-плагинов из имён файлов. После проверки ссылок в конфиге она выполняет каждый файл один раз и получает таблицу с обработчиками. Затем среда создаёт сервис ввода. Действия при запуске возвращаются из явного обработчика `load`.
2. Среда вызывает `load` и выполняет его действия до вызова `load` следующего плагина. Первыми идут `logger` и `builtin_primitives`, затем Lua-плагины по имени файла. Действия могут обращаться к самому плагину и к тем, чей `load` уже завершился. После загрузки всех плагинов сервис активирует `initial_mode`, а диспетчер доставляет события входа в поведения. Затем среда отправляет `ready`. Ввод и тики начинаются после обработки `ready`.
3. Ошибка на любом этапе запуска прерывает его. Среда сообщает об ошибке и вызывает `unload` в обратном порядке у плагинов, которые успели успешно пройти `load`. Если сам обработчик `load` возвращает ошибку, он освобождает созданные им ресурсы перед возвратом. Действия очистки могут обращаться к плагинам, которые ещё загружены.
4. При штатном закрытии среда прекращает приём нового ввода и тиков и отправляет `shutdown_started`. Она деактивирует поведения, освобождает удержания и доставляет события выхода, пока плагины загружены. Затем вызывает `unload` в обратном порядке, выполняет возвращённые действия и освобождает память каждого плагина. Ошибку выгрузки она записывает в журнал и продолжает закрытие. `builtin_primitives.unload` отпускает все оставшиеся клавиши и кнопки мыши, удерживаемые программой.

Таблица Lua и функции из неё живут между вызовами. Например, `local pending = {}` в начале файла создаёт таблицу, которую обработчики могут менять на тиках и читать в `unload`. При следующем запуске верхний уровень файла выполнится заново и создаст новую таблицу. Lua-обработчики `load` и `unload` получают свои события и контекст, как остальные функции из `event_handlers`. Пример файла `example.lua`:

```lua
local ticks = 0

return {
  event_handlers = {
    load = function()
      return {{ plugin = "logger", type = "log", arguments = { "debug", "Плагин загружен" } }}
    end,
    tick = function()
      ticks = ticks + 1
    end,
    unload = function()
      return {{ plugin = "logger", type = "log", arguments = { "debug", "Плагин выгружается", { ticks = ticks } } }}
    end,
  },
}
```

### События

Системные события доступны всем загруженным плагинам. События ввода среда направляет плагину активного поведения. Lua-плагин может вернуть таблицу `event_handlers`, где ключ — имя события, а значение — функция. Например, `stick_moved = on_stick_moved` связывает событие движения с функцией. Если обработчика события или всей таблицы нет, среда пропускает вызов. Для Rust действует то же правило.

| Событие | Когда возникает и что содержит |
| --- | --- |
| `ready` | После загрузки всех плагинов и активации начального режима, перед вводом и первым тиком. |
| `shutdown_started` | После остановки приёма ввода и тиков, пока плагины ещё загружены. |
| `tick` | По таймеру, даже без движения контроллера. Поле `dt_ms` — интервал с предыдущего тика. |
| `mode_changed` | После смены режима. Поля `previous_mode` и `new_mode` — имена старого и нового режимов. |
| `stick_behavior_entered` | Когда поведение становится активным для стика. Содержит `mode`, `source` и `behavior`. |
| `stick_behavior_exited` | Когда поведение перестаёт быть активным для стика. Содержит те же поля для прежнего поведения. |
| `trigger_behavior_entered` | Когда поведение становится активным для курка. Содержит `mode`, `source` и `behavior`. |
| `trigger_behavior_exited` | Когда поведение перестаёт быть активным для курка. Содержит те же поля для прежнего поведения. |
| `button_behavior_entered` | Когда становится активным поведение из `buttons.<имя>.behavior`. Содержит `mode`, `source`, `behavior` и имя кнопки в `button`. |
| `button_behavior_exited` | Когда это поведение перестаёт быть активным. Содержит те же поля для прежнего поведения. |

При смене режима среда сначала ставит в очередь выход из настроенных поведений старого режима, затем `mode_changed` и вход в поведения нового режима. В каждой группе первыми идут стики слева направо, затем курки слева направо и кнопки по имени. Поведение проходит выход и вход при переходе, даже если в обоих режимах указан один тип.

Предлагается одна очередь. События, которые среда создаёт при изменении состояния, обрабатываются после текущего списка действий. События перехода несут данные именно этого перехода, даже если режим успел снова смениться. Среда обрабатывает их до следующего тика или ввода контроллера. Для одного события все обработчики получают один снимок общего контекста. Возвращённые списки действий выполняются в порядке загрузки плагинов. В общий лимит цепочки входят и события, созданные средой при выполнении её операций. Это ограничивает, например, цикл из двух режимов, которые переключают друг друга при входе.

### События ввода контроллера

Движение и нажатие настраиваются независимо. Для каждого события среда ищет поведение нужного вида в активном режиме и направляет событие его плагину. Среда обновляет состояние и проверяет назначения в любом случае.

| Событие | Когда возникает и что содержит | Настройка поведения |
| --- | --- | --- |
| `button_pressed` | Когда кнопка переходит в нажатое состояние. Поле `button` содержит имя, например `lb`, `lsb` или `rt`. | `buttons.<имя>.behavior` |
| `button_unpressed` | Когда кнопка переходит в отпущенное состояние. Содержит то же поле `button`. | `buttons.<имя>.behavior` |
| `trigger_moved` | При изменении положения курка. Поле `value` содержит новое значение от 0 до 1. | `triggers.<сторона>.behavior` |
| `stick_moved` | При изменении положения стика. Поля `x` и `y` содержат новые координаты от −1 до 1. Положительные значения идут вправо и вверх. | `sticks.<сторона>.behavior` |

`lsb` и `rsb` — физические кнопки. Нажатие на стик меняет состояние кнопки, а отклонение стика меняет его координаты. Если человек одновременно отклоняет и нажимает стик, среда обрабатывает оба изменения отдельно.

Для `lt` и `rt` обработка ввода определяет состояние кнопки по фиксированному порогу. Выше 30% кнопка нажата, ниже 30% отпущена, ровно на 30% сохраняется предыдущее состояние. `button_pressed` и `button_unpressed` возникают при смене этого состояния. `trigger_moved` возникает при каждом изменении значения курка, в том числе при пересечении порога.

Например, когда правый курок переходит с 25% на 35%, среда создаёт `trigger_moved` и `button_pressed` для `rt` с одинаковым временем. Если `triggers.right.behavior` и `buttons.rt.behavior` заданы, каждое событие уходит по своей настройке. Если обе указывают на один плагин, он получает оба события, каждое со своим `behavior`.

Среда ищет назначение в режиме, активном на момент ввода. Если назначение переключает режим, среда доставляет события перехода и выбирает получателя ввода по новому активному режиму. При выходе из поведения плагин может очистить свои данные, связанные с удержанием.

Нажатие и отпускание отправляются по одному разу на переход, даже если оба пришлись между тиками. Удержание — часть состояния контроллера. На `tick` плагин видит, что зажато и с какого момента, и может сам задать длительность долгого нажатия или интервал повтора. На тике также можно двигать курсор и прокручивать страницу, пока стик остаётся отклонённым.

### Данные события и контекст

Ядро вызывает обработчик с двумя значениями: `event` описывает произошедшее, а `context` даёт снимок данных для чтения. У каждого события есть `type`, `time_ms` и `unix_ms`. `time_ms` отсчитывает миллисекунды от запуска и подходит для измерения длительности нажатия. `unix_ms` отсчитывает миллисекунды с начала эпохи Unix и подходит для журнала. Адаптер ставит обе метки времени ввода до передачи события в очередь.

В событиях ввода и смены поведения `mode` указывает, к какому режиму относится событие. В событиях ввода `input_mode` указывает режим на момент ввода, до выполнения назначения. Поле `source` описывает физический источник. У стика или курка это `kind` и `side`. У обычной кнопки это `kind = "button"` и `id`. Поле `behavior` содержит `plugin`, `type`, список `arguments` и настройки из YAML, если они заданы. Для `button_pressed` поле `button` остаётся именем для `mappings`, а `source` позволяет отличить обычную кнопку, клик стика и порог курка.

Например, в Lua событие движения правого стика в режиме текста выглядит так:

```lua
{
  type = "stick_moved",
  time_ms = 12480,
  unix_ms = 1762600000000,
  input_mode = "text",
  mode = "text",
  source = { kind = "stick", side = "right" },
  behavior = { plugin = "chord_text", type = "choice", arguments = {} },
  x = 0.78,
  y = -0.12,
}
```

В контексте обработчика доступны:

| Поле | Что содержит |
| --- | --- |
| `active_mode` | Имя активного режима по данным среды. |
| `controller` | Снимок контроллера от среды. Включает положение стиков, значения курков и состояние кнопок. Для удерживаемой кнопки есть `pressed_at_ms` в той же шкале времени, что и `event.time_ms`. |
| `time` | `monotonic_ms` для интервалов и `unix_ms` для календарного времени. В обработчике события они совпадают с `event.time_ms` и `event.unix_ms`. Обработчик действия получает время начала вызова. |
| `config` | Разобранный YAML целиком. |
| `plugins` | Имена плагинов, найденных при запуске. |
| `state` | Данные, сохранённые ядром для этого плагина. |
| `origin` | В контексте действия — имя плагина, который его вернул, и идентификатор активации поведения, если действие пришло из него. |

### Возможные дополнительные события

Для обсуждения предлагаются `controller_connected` и `controller_disconnected`. Среда создаёт их по сообщениям от адаптера `gamepad`. При потере связи плагин сможет сразу отменить незавершённый ввод, например отсчёт подтверждения символа. Сброс снимка контроллера и освобождение удерживаемых клавиш и кнопок мыши выполняет среда при обнаружении отключения. При повторном подключении плагин сможет начать с нового снимка контроллера.

### Где хранится состояние

Плагин может хранить внутренние данные в своём экземпляре Rust или в Lua-таблицах и переменных, созданных при загрузке файла. Для данных, которые удобно передавать явно, среда также предоставляет `context.state`. Плагин может вернуть обновление этого поля рядом со списком действий. Для этого обработчик возвращает таблицу `{ actions = ..., state = ... }`. Среда принимает обновление после успешного вызова, до выполнения списка. Ошибка в последующем действии обрабатывается отдельно.

Например, `chord_text` может хранить время начала подтверждения, пару выбранных секторов, углы стиков, состояние регистра и признак, что символ уже введён за это удержание. Сам ввод в систему выполняет `builtin_primitives` по запросу Action Performer.

Данные каждого плагина живут отдельно. Плагин сбрасывает временные данные при выходе из режима, а настройки, которые нужны при повторном входе, может оставить до выгрузки.

## Логирование

Предлагается встроенный Rust-плагин `logger` с действием `log`. У действия два обязательных аргумента: уровень (`trace`, `debug`, `info`, `warn` или `error`) и текст сообщения. Третий аргумент — необязательный словарь с деталями, например с именами режима и кнопки. Имя плагина, вернувшего действие, и время записи среда передаёт автоматически.

```yaml
plugin: logger
type: log
arguments:
  - debug
  - Режим переключён
  - { previous_mode: normal, new_mode: text, input: ls }
```

Внутри `logger` предлагается использовать `tracing` и `tracing-subscriber`. Для первой версии достаточно читаемых строк в `stderr` и фильтра `RUST_LOG` через `EnvFilter` с уровнем `info` по умолчанию. Дополнительный словарь записывается одним полем `fields`. [Документация tracing](https://docs.rs/tracing/latest/tracing/), [форматирование](https://docs.rs/tracing-subscriber/latest/tracing_subscriber/fmt/index.html), [фильтрация](https://docs.rs/tracing-subscriber/latest/tracing_subscriber/filter/struct.EnvFilter.html).

Lua и Rust могут вернуть `logger.log` из любого обработчика, включая `load` и `unload`. Ошибки среды, например при чтении YAML или выполнении действия, пишет сама среда через этот же журнал. До запуска логгера и при ошибке самого логгера сообщение выводится напрямую в `stderr`.

## Ввод текста двумя стиками

В режиме `text` Lua-плагин `chord_text` получает оба поведения. Левый стик с типом `group` выбирает группу, правый с типом `choice` — символ внутри неё. Плагин читает положение обоих стиков при входе в режим, следит за изменениями по `stick_moved` и проверяет время подтверждения на `tick`. В `example/config.yaml` есть таблицы `en`, `ru` и `symbols`. В режиме `exact` число секторов фиксировано. Пустые позиции в неполной таблице пропускаются. В режиме `adaptive` число левых секторов следует числу групп, а число правых — числу символов в выбранной группе.

Сектора каждого стика равны по ширине. Середина первого сектора направлена строго вверх. Остальные идут по часовой стрелке. При четырёх секторах их середины идут в порядке вверх, вправо, вниз и влево.

### Выбор таблицы

При запуске активна первая таблица в `chord_text.keymaps` по порядку в YAML. Порядок должен быть доступен плагину. В текущем примере это `en`, затем `ru`, затем `symbols`.

В режиме `text` кнопка `LB` переключает таблицы по кругу. Крестовина отправляет клавиатурные стрелки для перемещения курсора в активном приложении. Кнопка `X` отправляет Backspace.

| Действие `chord_text` | Что делает |
| --- | --- |
| `select_keymap` | Выбирает таблицу по имени, переданному в `arguments`, например `ru`. При неизвестном имени возвращает ошибку и сохраняет текущий выбор. |
| `next_keymap` | Выбирает следующую таблицу. Предлагается переходить с последней на первую. |
| `previous_keymap` | Выбирает предыдущую таблицу. Предлагается переходить с первой на последнюю. |

При фактической смене таблицы плагин сбрасывает отсчёт и предыдущий подтверждённый выбор. Если правый стик отклонён, плагин ждёт его возврата в центральную зону. Если правый стик уже в центре, новый выбор доступен сразу. В обоих случаях для подтверждения следующего символа правый стик нужно заново отклонить.

### Подтверждение выбора

Когда оба стика отклонены и выбрана существующая пара секторов, плагин запоминает углы обоих стиков и запускает отсчёт. Каждый стик должен остаться в своём секторе и держаться в пределах нескольких градусов от своего угла в начале отсчёта. Отправная точка — фактическое положение стика. Например, следующий отсчёт может начаться сразу после кругового движения в новый сектор.

Если любой стик вернулся в центральную зону, сменил сектор или вышел за угловой допуск, прежний отсчёт сбрасывается. Когда снова есть допустимая пара, начинается новый отсчёт. Угол сравнивается по кратчайшей дуге, поэтому переход с 359° на 1° равен 2°. Тик подтверждает символ, когда пара удержалась заданное время, даже если контроллер больше не присылает движения. Пробные значения для настройки:

```yaml
chord_text:
  confirm:
    stable_ms: 60
    angle_tolerance_deg: 5
```

### Следующий символ и повтор

После подтверждения можно сразу перейти в другой сектор. Например, левый стик остаётся на группе, а правый движется по кругу до сектора следующей буквы. Каждая новая пара проходит своё подтверждение.

Удержание подтверждённой пары вводит символ один раз. Для повторного ввода той же пары подряд нужно вернуть правый стик в центральную зону и снова выбрать символ. Короткий заход в другой сектор без подтверждения сохраняет блокировку предыдущей пары. Когда подтверждена другая пара, к прежней можно вернуться сразу.

Действие `chord_text.repeat_choice` позволяет повторить символ, пока стики остаются в уже подтверждённой паре. Предлагается выводить тот же символ с тем же регистром один раз на вызов, без нового отсчёта.

Одна буква может стоять в нескольких группах. Каждая позиция считается отдельным выбором, поэтому переход к другой позиции той же буквы вводит её повторно.

### Группы на кнопках-модификаторах

Кнопке назначается поведение `chord_text` типа `modifier_key`. Её группа задаётся под именем кнопки в `chord_text.modifier_groups`. Например, группа для `B` находится в `chord_text.modifier_groups.b`. Пока кнопка зажата, левый или правый стик выбирает символ из этой группы. Если зажато несколько модификаторов, действует группа последней нажатой кнопки. После её отпускания снова действует группа предыдущей удерживаемой кнопки.

В `exact` число направлений берётся из `sectors.choices`. В `adaptive` оно равно длине группы в символах. Первый символ соответствует направлению вверх, остальные идут по часовой стрелке.

Если стик уже отклонён при смене группы, выбор начинается после смены направления или возврата в центр. Первый стик, начавший выбор, управляет им до возврата в центр. Символы подтверждаются с той же задержкой, что и буквы. После отпускания последнего модификатора использованный стик должен пройти через центр, прежде чем возобновится ввод двумя стиками.

### Верхний регистр

В примерной раскладке в режиме `text` у кнопки `RB` задано поведение `chord_text` типа `uppercase`. Короткое нажатие после отпускания включает верхний регистр для следующей буквы. Знаки препинания его не сбрасывают. Долгое удержание включает верхний регистр сразу по достижении порога. Отпускание выключает его и не включает регистр для следующей буквы.

Порог задаётся в `chord_text.uppercase.hold_ms` и по умолчанию равен 250 мс. Для отдельной кнопки его можно переопределить в `behavior.settings.hold_ms`. Действие `chord_text.uppercase` с аргументом `once` по-прежнему включает верхний регистр для одной буквы, а с аргументом `caps` переключает постоянный верхний регистр.

### Что сохраняется после выхода

Правила хранения таблицы и `caps` задаются отдельно в `chord_text.options`. Их применяет Lua-плагин. Для него сеанс ввода заканчивается, когда перестаёт быть активным хотя бы одно из двух поведений `group` и `choice`. При выходе плагин сбрасывает отсчёт и текущий выбор символа.

```yaml
chord_text:
  options:
    keymap_on_exit: keep
    caps_on_exit: reset
```

- `keep` хранит значение в памяти и сохраняет его между входами в режим до закрытия программы. При следующем запуске активна первая таблица из YAML, а `caps` выключен.
- `reset` возвращает таблицу к первой по порядку в YAML или выключает `caps`, в зависимости от настройки.

В примере предложено сохранять таблицу и сбрасывать `caps` по умолчанию.

## После MVP

Отдельный встроенный плагин на Rust предоставит действия macOS. Например, `macos.next_window` переключит окно средствами системы. Плагин сможет использовать системные API и заранее подготовленные AppleScript-сценарии. Каждая такая операция будет доступна как именованное действие через Action Performer.
